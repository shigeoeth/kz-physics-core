Уже сделано в этой среде:
- аудит прочтения кода (movement-spec.md);
- прогнаны `npm test` (2 падения из 72), `npm run typecheck` (OK),
  `npm run build` (OK, dist совпадает по составу с src);
- зафиксировано: git-история потеряна (1 коммит), версии расходятся
  (package.json 0.1.0 / lockfile 0.4.1), provenance source-sdk-2013 —
  только заявление авторов.

Осталось (нужны данные от владельца проекта):
- [ ] commit hash / tarball оригинального форка, который реально использовался
      в игре; diff с текущим кодом;
- [ ] конфигурация @unsurf/cs-movement, использовавшаяся в основном проекте
      (значения autobhop/bhopSpeedClamp/noPrestrafe/airAccelerate/perf/stamina);
- [ ] запись воспроизводимого Long Jump из игры (tick-by-tick input + snapshot
      состояния на takeoff), для эталонного прогона в harness.

Критерий приёмки: pinned baseline-коммит в этом репо + документированный diff
с «игровым» форком; зелёный или честно-красный список тестов зафиксирован.

## Этап 1 — Headless harness (ПЕРВАЯ ЗАДАЧА, см. handoff.md)

Сцены описываются декларативно (brush-лист), старт = {origin, velocity, yaw,
input-программа по тикам}, выход = CSV/JSON история (tick, origin, velocity,
onGround, surfing, contacts). Никаких изменений в src/.

Критерий приёмки: детерминизм (два прогона → бит-в-бит одинаковый JSON),
отсутствие NaN, golden-файл закоммичен.

## Этап 2 — Простые независимые сцены

плоскость / стена / внутренний угол / step 18 / ramp под порогами 0.7 /
seam двух brush. Для каждой — ожидаемое поведение формулируется ДО запуска,
по возможности с аналитическим предсказанием (например, время полёта LJ
flat-ground ≈ 2·JUMP_VELOCITY/GRAVITY ≈ 0.755 c ⇒ ~96.6 тиков @128).

## Этап 3 — Базовое движение и прыжок (CS:GO base profile)

Отделяем профиль «CS:GO native» от chasemod-гибрида: конкретные значения
sv_airaccelerate, surface friction pipeline, jump impulse, deadstrafe —
каждое только после сверки с внешним эталоном (source-provenance.md §3).
Что не подтверждено эталоном — остаётся флагом/параметром, не «правдой».

## Этап 4 — KZT режимный слой

Подтверждённые изменения режима (autobhop-политики, prestrafe-cap'ы, stamina,
teleport/block rules GOKZ) — поверх базового профиля, через явные profile-объекты.
GOKZ порт не начинается до получения архива и проверки лицензии.

## Этап 5 — Adapter к основному проекту

Контракт (будущий, в этом репо не реализуется):
- вход: TickCommand { dt=1/128 fixed, buttons, angles };
- выход: Snapshot { origin, velocity, onGround, ducked, … } + события
  (takeoff, land, blocked) для Entity I/O / timer / jumpstats / replay;
- Three.js/DOM остаются снаружи; movement core не импортирует их.
- Запрет: post-tick replacement velocity, оставляющая position от другой
  схемы. Если нужна коррекция — только внутри единого tick-алгоритма.

Ladder/water/special modes — отдельные этапы с собственными критериями,
после Этапа 5.

## Риски

- Дефолты библиотеки смешивают режимное и базовое поведение — при миграции
  легко принять chasemod-гибрид за CS:GO. Лечение: профили вместо дефолтов.
- Два падающих теста описывают поведение, которого код не даёт; нельзя
  «починить» их молча — каждое изменение флага/формулы отдельным diff'ом
  с объяснением, что оно меняет в измерениях.
